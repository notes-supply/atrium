Restic backups on apollo

Version 23, today at 08:12 by blackbox. What changed.

Summary

apollo runs restic every night against two repositories. The first lives on the cluster's replicated pool, tank, and answers most restores in seconds. The second is offsite, on a borrowed disk at a friend's flat, reached over the tailnet through the rules in Tailnet ACLs.

Nothing here needs a person on a normal night. Whoever writes this page reads the job logs at 06:00 and changes a line only when something changed, so a quiet page means a quiet week. The wiki folder itself is saved by the autosave service, not by these jobs.

Restore a file

Find the snapshot first, then restore into a scratch folder and copy back by hand. Restoring in place has bitten once already; see known issues.

Restore drill, November

Once a month three files are picked at random and restored from each repository. This month:

  • A 1.2 GB photo folder came back from offsite in 14 minutes, at about 1.4 MB/s.
  • The wiki's hourly snapshot from 02:00 matched the record byte for byte.
  • A notes file from September restored from tank in under a second.
  • The check --read-data-subset=5% pass found no damaged packs.

Known issues

  1. The offsite job stalls when a node of apollo sleeps mid-run. It resumes on its own, but the morning summary reports it as failed.
  2. Restoring in place over a file that the sync client holds open leaves a zero-byte file. Restore to /tmp first.

Open questions

  • Should the offsite copy run weekly instead of nightly while the borrowed disk is this slow?
